## The review questions

1. **Where does authentication happen, and how does `user_id` stop being controlled by the payload?** `POST /auth/token` (`src/auth/`) checks the demo credentials (scrypt) and issues an HS256 JWT whose `sub` is the merchant and whose role is `merchant` or `operator`. The auth plugin verifies the Bearer token on every route except `/health`, `/ready` and `/auth/token` and sets the principal. `/chat` takes the merchant from the principal; a `user_id` in the body is only accepted when it equals it (otherwise 403 `user_mismatch`, before any model call), and the Support tools are created with the principal's id bound by closure, so the model never chooses whose data it reads. Tests: `tests/integration/auth.test.ts`, `chat.test.ts`; eval N4, N5, `no_cross_merchant_data`.
2. **How does the conversation survive between requests and after a restart?** `/chat` returns a `conversation_id`; conversations and messages live in SQLite (WAL) on the `app-state` Docker volume, owned by the merchant (another merchant gets 404). Each turn loads the conversation, gives the Router and the agents a rolling summary plus the last six messages, and rewrites follow-ups into a standalone question; compaction is deterministic. The JWT key is persisted next to the database, so tokens issued before a restart stay valid. Evidence: `docs/evidence/restart.log` (`scripts/restart-evidence.sh`); tests `memory.test.ts`, `context.test.ts`; eval MT1, MT2.
3. **How does an operator receive a ticket, reply and return control to the agent?** The agent interrupts the run (a request for a person, or a sensitive action: `request_terminal_replacement`) and a `handoffs` row is written with the checkpoint and the evidence. An operator (own login, role `operator`) lists the queue with `GET /operator/handoffs` and resolves it with `POST /operator/handoffs/:id/resolve` (`approve`, `reject` or `reply`, with `expected_version`: a second resolve gets 409). Approve and reject resume the saved run from the checkpoint and the outcome reaches the conversation exactly once (`UNIQUE(messages.handoff_id)`); a reply is delivered to the merchant and the agent sees it on the next turn (declared limit). Pending handoffs expire after `HANDOFF_TTL_MINUTES`, interrupted resolutions are finished at boot, and every step is in the append-only audit log. The UI has the operator console. Tests: `tests/integration/hitl.test.ts`; eval H1–H3, N2, N3; UI smoke.
4. **How is the final answer proved factually correct and grounded?** `npm run eval` runs the golden set against the deployed API, three times, and an independent judge of another model family (qwen locally; Claude as the reference) scores groundedness against the recorded evidence (tool outputs, retrieved excerpts), correctness against the reference facts in `eval/golden.json`, relevance, helpfulness and safety. Canaries with known defects detect an unreliable judge; a baseline with a regression gate (zero tolerance on the security checks) blocks regressions; every report records the API build and the runner commit. At run time the output guardrail requires sources and checks every amount or percentage against the evidence (`guardrails/output.ts`): a value that is not there is replaced and the turn goes to a person. Where the answers are not correct (RAG on the 8B), the reports say so and the README repeats it.
5. **What makes the system replan after observing a specialist's result?** `orchestration/replanner.ts` decides after each specialist: an offline machine in `get_terminal_status` adds Knowledge (which also receives the troubleshooting guide searched in code), a crashed Support tool escalates to a person, unavailable live data finishes without a person; the orchestrator then joins Support's facts and Knowledge's guidance in code. Tests: `replan.test.ts`; eval R1 (`replanned` 1.0).
6. **Which artifacts prove that Docker, the live evaluation and the critical flows were executed?** `eval/reports/` (every report with the API build and the runner commit) and `eval/baseline.json`; `docs/evidence/restart.log`, `metrics.json` and `gpu.log`; `.github/workflows/ci.yml` (typecheck, tests, compose validation, image build, container smoke with a restart); the UI's `scripts/smoke.mjs` (26 end-to-end checks); `docs/timesheet.md` with the commit timeline.
